# ADR-0003. 동시성 제어: 수납 건 사이의 경쟁은 DB 제약으로 막는다

상태: 채택(INV-03, INV-05) · 실험중(INV-04, INV-10) · 갱신: 2026-11-16

## 1. 맥락 (Context)

수납 건 사이의 규칙 두 가지는 순서대로 부르면 서비스의 확인으로 지켜진다.

| 불변식 | 서비스의 확인 | 위반 시나리오 |
| :--- | :--- | :--- |
| INV-05 한 산정에 수납 건 하나 | 수납 건을 만들기 전에 `existsByInvoiceId` | C-06 두 창구가 같은 산정으로 같은 순간에 첫 결제를 받는다 |
| INV-03 오더 항목은 완료된 수납 건 하나에만 | 완료하기 전에 `findOrderItemIdsIn(COMPLETED)` | C-03 같은 항목을 가진 두 수납 건이 같은 순간에 완료한다 |

두 확인 모두 확인과 커밋 사이에 틈이 있다. READ COMMITTED에서는 다른 트랜잭션이 아직 커밋하지 않은 행이 보이지 않는다. 그래서 두 호출이 그 틈에 겹치면 둘 다 "없음"을 보고 둘 다 반영한다.

방어 방법을 고를 때 갈리는 기준은 **막아야 할 행이 확인하는 시점에 이미 있느냐**다.

- C-06은 첫 결제라 수납 건 행이 아직 없다.
- C-03은 두 모양이 있다.
  - 두 수납 건이 이미 진행 중이면 행이 있다.
  - 두 수납 건이 모두 이번 호출에서 새로 생겨 한 번에 다 내면, 서로의 행이 커밋 전이라 보이지 않는다.

INV-04(C-04 완료와 오더 취소, C-05 소멸과 완료)는 `order`가 수납 건의 사실을 확인하는 방식이 먼저 정해져야 해서 ADR-0002 뒤로 미룬다. INV-10(환불 몫)은 환불 슬라이스에서 다룬다.

## 2. 고려한 대안 (Alternatives)

| 후보 | 핵심 아이디어 |
| :--- | :--- |
| (가) DB 제약 | 규칙을 유일 제약이나 함수 기반 유일 인덱스로 표현한다. 뒤에 쓴 쪽은 앞쪽 커밋을 기다렸다가 ORA-00001로 실패한다. |
| (나) 비관적 잠금 | 확인하기 전에 관련 행을 `SELECT ... FOR UPDATE [NOWAIT]`로 잠가 줄을 세운다. |
| (다) 낙관적 잠금 | 엔티티에 `@Version`을 두고, 고칠 때 버전이 그대로인지 확인한다. |
| (라) 애플리케이션 락 | `synchronized`나 메모리 락으로 같은 산정·항목의 호출을 줄 세운다. |
| (마) 다른 모듈의 행 잠금 | 이미 있는 행인 산정(`billing`), 오더 항목(`order`), 내원 건(`reception`)을 잠근다. |
| (바) SERIALIZABLE | 격리 수준을 올린다. |

## 3. 실험 및 측정 (Experiments)

**방법**
- Oracle Free 23(Testcontainers), READ COMMITTED에서 돌렸다.
- 서비스가 틈 한가운데에서 부르는 대역(`invoiceQueryService.invoice`, `orderItemQueryService.statusesOf`)이 `CountDownLatch(2)`로 상대 스레드를 기다리게 했다. 두 스레드가 모두 확인을 통과했고 아무도 커밋하지 않은 상태를 매번 만든다.
- 기다림에는 2초 제한을 둔다. 잠금으로 방어하면 한쪽이 그 지점에 오지 못하는데, 제한이 없으면 서로를 기다리며 멈추기 때문이다.

**확인한 것**
- 방어 방법과 상관없이 지켜야 하는 두 가지만 본다.
  - 규칙: 불변식이 지켜졌다.
  - 응답 = 기록: 성공 응답을 받은 결제는 모두 저장돼 있다.
- 어느 쪽이 무슨 예외를 받는지는 방어 방법마다 달라서 보지 않는다.

**재현 명령**
```bash
./gradlew test --tests 'com.htsemr.payment.PaymentConcurrencyTest'
```

| 테스트 | 방어 없음 | (나) 잠금 | (가) DB 제약 (V9, V10) |
| :--- | :--- | :--- | :--- |
| `같은 산정으로 동시에 첫 결제를 받아도 수납 건은 하나이고 성공한 결제는 모두 남는다` (C-06) | 실패: 수납 건 2 | 해당 없음(잠글 행 없음) | 통과: 수납 건 1, 성공 1 |
| `같은 항목을 가진 두 수납 건이 동시에 완료해도 완료되는 수납 건은 하나이고 성공한 결제는 모두 남는다` (C-03, 행 있음) | 실패: 완료 2 | 통과 | 통과: 완료 1 |
| `같은 항목을 가진 두 새 수납 건이 한 번에 다 내며 동시에 완료해도 완료되는 수납 건은 하나다` (C-03, 행 없음) | 실패: 완료 2 | **실패: 완료 2** | 통과: 완료 1 |

- **(나)의 실험 방식:** 완료 확인 직전에 "이 항목을 가진 수납 건" 행을 모두 `PESSIMISTIC_WRITE`로 잠그는 쿼리를 잠시 넣고 돌렸다. 커밋하지 않고 되돌렸다.
- **(가)에서 진 쪽이 받은 오류:** 리포트에 `ORA-00001 ... UK_PAYMENT_INVOICE`와 `ORA-00001 ... UK_PAYMENT_ITEM_COMPLETED`가 찍혔다.

결정한 계약을 확인하는 테스트는 다음 두 개다. 둘 다 통과한다.
- `동시에 첫 결제가 겹쳐 진 창구는 다시 시도하라는 예외를 받고, 다시 시도하면 먼저 만든 수납 건에 이어서 받는다`
- `같은 항목의 완료가 겹쳐 진 창구는 결제가 저장되지 않았다는 예외를 받고, 다시 시도하면 완료가 막힌 결과를 받는다`

**변이 검사: 테스트가 방어를 실제로 확인하는지**
- 완료할 때 항목에 완료를 표시하는 줄(`markCompleted`)을 빼면 C-03 테스트 3개가 실패한다.
- 제약 위반을 도메인 예외로 바꾸는 조건을 끄면 C-06의 재시도 테스트가 실패한다.

**실험하지 않고 근거로 제외한 후보**
- (다) `@Version`
  - C-06은 고칠 행이 없다.
  - C-03은 두 수납 건이 서로 다른 행이라, 각자 자기 버전만 올려서 부딪히지 않는다.
- (라) 애플리케이션 락
  - 서버 한 대 안에서만 통한다. 서버를 2대로 돌리거나 무중단 배포로 옛 서버와 새 서버가 겹치면 뚫린다.
- (마) 다른 모듈의 행 잠금
  - 행이 늘 있어서 (나)의 구멍은 메울 수 있다.
  - 하지만 `payment`가 다른 모듈의 테이블을 잠그게 되어 모듈 경계를 넘는다(modules/README).
- (바) SERIALIZABLE
  - Oracle의 SERIALIZABLE은 스냅숏 격리다. 서로 다른 행을 새로 쓰는 두 트랜잭션(write skew)을 막지 않으므로 C-06과 C-03을 그대로 통과시킨다.

## 4. 최종 결정 및 근거 (Decision)

**(가) DB 제약을 수납 건 사이 경쟁의 마지막 방어선으로 둔다.**

| 불변식 | 제약 |
| :--- | :--- |
| INV-05 | `payment.invoice_id` 유일 제약 `uk_payment_invoice` (V9) |
| INV-03 | `payment_item.completed` 표시와 함수 기반 유일 인덱스 `uk_payment_item_completed` (V10). `case when completed = 1 then order_item_id end`라서 완료된 항목끼리만 유일하다. 진행 중인 수납 건끼리나, 거부된 수납 건과는 같은 항목이 겹쳐도 된다. |

**근거**
- 세 가지 모양을 모두 막은 후보는 (가)뿐이다(3절 표).
- (나)는 "행이 없는" 모양에서 실패했다. 유일 인덱스는 커밋되지 않은 키도 보므로 행이 있든 없든 막는다.
- 규칙이 DB에 있으므로 서버 대수나 코드 경로와 상관없이 지켜진다.

**서비스는 이렇게 맞춘다**
- 순서대로 오는 경우를 위한 확인은 그대로 둔다. 그래야 먼저 알 수 있는 경우에 분명한 응답을 줄 수 있다.
  - 끝난 산정: `InvoiceAlreadyUsedException`
  - 이미 수납된 항목: `CompletionBlocked` 결과
- 저장은 `saveAndFlush`로 바로 반영한다. 완료 표시(UPDATE)는 그냥 두면 커밋할 때 반영되어, 위반이 서비스 밖에서 난다. 그러면 서비스가 잡아서 바꿀 수 없다.
- 두 제약의 위반은 제약 이름으로 가려 도메인 예외로 바꾼다. 그 밖의 위반은 그대로 던진다.
  - `uk_payment_invoice` → `PaymentStartConflictException`: 다시 시도하면 먼저 만든 수납 건에 이어서 받는다.
  - `uk_payment_item_completed` → `PaymentCompletionConflictException`: 결제가 저장되지 않았다. 다시 시도하면 `CompletionBlocked`를 받는다.

**T-PAY-04 감지 시점(동시 수납 부분)**
- 동시 수납은 **완료를 시도할 때** 감지한다.
- 수납을 시작할 때는 같은 항목의 다른 수납 건이 진행 중이어도 막지 않는다. 다시 산정할 수 있고, 어느 쪽이 먼저 완료할지 모르기 때문이다.
- 오더 변경 부분은 ADR-0002와 함께 정한다.

## 5. 영향 및 트레이드오프 (Consequences)

**강제 시점**
- INV-03, INV-05가 `미정(ADR-0003)`에서 `즉시`로 바뀐다. 순서대로 오면 서비스의 확인이, 동시에 오면 DB 제약이 막는다.

**감수한 단점**
- **C-03에서 진 쪽은 결과가 아니라 예외를 받는다.**
  - 순서대로 왔다면 결제를 남기고 `CompletionBlocked`를 받았을 경우다.
  - 제약 위반은 트랜잭션을 롤백시키므로 그 호출의 결제를 남길 수 없다. 창구는 받은 돈을 돌려줘야 한다.
  - 응답(실패)과 기록(없음)은 어긋나지 않는다. 같은 항목을 두 창구가 같은 순간에 완료하는 일은 드물다고 보고 감수한다.
  - (나)라면 진 쪽도 결과를 받을 수 있지만, 행이 없는 모양을 막지 못한다.
- **같은 사실을 두 곳에 둔다.** `payment_item.completed`는 수납 건의 `COMPLETED`와 같은 사실이다.
  - 완료 표시는 `Payment.complete` 한 곳에서만 한다.
  - 완료된 수납 건을 환불로 취소할 때 이 표시를 지워야 한다(환불 슬라이스).
- **Kotlin 상수와 마이그레이션의 제약 이름이 묶인다.** 이름이 어긋나면 변환이 조용히 빠진다. 재시도 테스트가 이를 지킨다.
- **진 쪽은 앞쪽 트랜잭션이 끝날 때까지 기다린다.** 수납 트랜잭션은 짧아 대기 시간 제한을 따로 두지 않았다. 카드 승인처럼 외부 호출이 트랜잭션 안에 들어오면 다시 본다.

**남은 것**
- INV-04 (C-04, C-05): ADR-0002 뒤에 정한다.
- INV-10 (C-11): 환불 슬라이스에서 정한다.
- **실험 중 새로 찾은 틈(위반 시나리오 목록에 없음):**
  - 같은 진행 중인 수납 건에 두 창구가 같은 순간에 결제를 붙이면, 둘 다 자기 사본에서 A-20을 통과해 결제 합계가 본인부담 합계를 넘을 수 있다.
  - 이 경우는 행이 이미 있으므로 `FOR UPDATE NOWAIT`이나 `@Version`이 후보다.
